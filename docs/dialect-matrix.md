# Dialect × Upstream compliance matrix — x2api template

**Scope.** Rows = upstream providers {OpenAI, DeepSeek, GLM, Anthropic}; columns = the template's inbound dialects **as these probes took them** {`/v1/chat/completions`, `/v1/messages`, `/v1/responses`} — the fourth, Gemini's `/v1beta/models/{model}:generateContent`, arrived after this snapshot and is assessed in the follow-up note under §1. Built from the four source-verified reports in `docs/compliance/{openai,deepseek,glm,anthropic}.md` (all dated 2026-09-06, read in full), the live template tree (`crates/x2api-kit/src/provider.rs`, `crates/service/src/provider.rs`, the bridge crates, `x2api-server/src/{routes,errors}.rs`), plus **today's live route probes and three web re-verifications** (Anthropic's OpenAI-SDK compatibility layer, DeepSeek Responses guide, Z.AI coding-plan endpoint table). No repo edits.

**Legend (cell = what it takes to serve that inbound dialect from that upstream).**
- **NATIVE** — upstream endpoint speaks the dialect itself; the `service` relay (or a zero-translation passthrough) reaches it with config only.
- **IR-BRIDGE** — inbound bridge folds the dialect to the chat-completions IR and a chat-speaking provider serves it (viable, with the loss list in §1b).
- **PROVIDER-CRATE** — needs vendor wire translation beyond chat-completions.
- **GAP** — neither route works (reason given).

### 1c. Short gap list

- **G1 — CLOSED (fidelity lane).** The seam exists: `Provider::native_dialects()` + `relay_raw()` (`x2api-kit/src/provider.rs`; `Dialect`/`RawReply`/`RawFrames`) — a provider whose upstream natively speaks a client dialect relays request and reply BYTES end-to-end: no IR, no fold, shapes the IR cannot carry survive intact, non-2xx vendor envelopes pass through untouched. The four upstream-native non-chat surfaces (DeepSeek `/responses`, `/anthropic`; GLM `/api/anthropic`, `/api/v1/responses`; Anthropic `/v1/messages`) are pass-through candidates for any crate that declares the dialect (pinned by the `fidelity_lane_*` tests in `x2api-server/tests/api.rs`). What the lane deliberately does NOT do: rewrites (aliases belong inside `relay_raw`, in code), retries (single attempt — a committed vendor stream is never re-sent), and for `Dialect::Chat` it opts out of sentinel enforcement, so `stream_relay` stays the protected chat fast path.
- **G2 — CLOSED (function tools).** The IR types tool calls and all three non-chat folds translate them in both directions, so a tool-using Claude, Responses or Gemini client is served from any OpenAI-dialect upstream.
- **G2b — CLOSED (request-side media).** An Anthropic `image`/`document`, a Responses `input_image`/`input_file`, or a Gemini user-turn `inlineData` folds into the chat `image_url`/`file` part that vision- and document-capable OpenAI-shape vendors accept, built by `x2api_kit::{image_part, file_part, file_ref_part, data_url, parts_content}` so no fold invents a private media shape (Gemini keeps the client's part order through `parts_content`, and composes its raw base64 into a data URL with `data_url`). What stays open is precisely what the chat dialect cannot say — media outside a user turn, media returned BY a tool, an image `file_id`, a hosted-`url` document (Gemini's `fileData` is that case), a part claiming two oneof arms at once, and a block CLAIMING what the wire cannot honour (`citations` enabled, a non-empty `title`/`context`, `oversized_image: "error"`) — plus audio and **media OUTPUT**, which has no IR field at all (`Completion.text` reads `message.content` as a string) and exists only for vendors with an image-generation tool.
- **G2c — the two residuals G2b closes on purpose.** A folded document `file_id` is only resolvable where the id was minted: it works against the upstream that owns that file store (a Responses client's OpenAI id against OpenAI) and 400s at DeepSeek/GLM — the deployment/fidelity-lane line, not a fold gap, since a bridge does no I/O and cannot dereference a vendor file. Cache hints go by whether the target wire defines them: `prompt_cache_breakpoint` is forwarded onto the folded media part (chat's own `image_url`/`file` types carry it), Anthropic's `cache_control` is dropped (no chat counterpart) — neither is refused, because refusing cached traffic for zero fidelity gain is its own outage.
- **G3 — Responses inbound has no state** (the tool round-trip is CLOSED: `function_call`/`function_call_output` items fold, and the stream emits `output_item.added` + `function_call_arguments.delta`/`.done`) (§1b row 2); DeepSeek's own Responses surface is also stateless, so the fold matches upstream there, but OpenAI-native `store`/chains cannot be honoured.
- **G4 — CLOSED (Anthropic error taxonomy).** `anthropic_kind` derives `error.type` from the vendor's own status table (`crates/x2api-server/src/errors.rs::anthropic_kind`): 503 **and** 529 → `overloaded_error`, plus 402 `billing_error`, 404 `not_found_error`, 409 `conflict_error`, 413 `request_too_large`, 408/504 `timeout_error`, with unknown statuses falling through to `api_error` rather than being guessed at. The closed set is `ANTHROPIC_KINDS` (`crates/x2api-server/src/errors.rs::ANTHROPIC_KINDS`): its test sweeps 100..=599 and proves every status renders a member, so an invented kind cannot return unnoticed; `every_kind_matches_the_vendors_table` pins the mapping against `anthropic.md` (b)3.
- **G5 — `GET /v1/models` remains OpenAI-shaped; Anthropic's page grammar is open.** This is now much narrower than the old format-blind/no-context finding: `Provider::models` accepts `CallContext`, and both OpenAI and Gemini listings pass through the same client gate + admission preamble and shared retry loop before rendering (`crates/x2api-kit/src/provider.rs::Provider::models`, `crates/x2api-server/src/routes.rs::models`, `crates/x2api-server/src/routes.rs::list_models`, `crates/x2api-server/src/routes.rs::admit`, `crates/x2api-server/src/routes.rs::fetch_listing`). The credential half is **largely closed**: the reference provider receives context but deliberately keeps its configured credential authoritative, so provider-crate policy may use or reject caller credentials. What remains is adding an Anthropic model-page render and endpoint without misusing the OpenAI `/v1/models` grammar.
- **G6 — entitlement/ToS:** GLM's Anthropic + Responses bases are Coding-Plan-scoped and "limited to use within the
  following officially supported tools" (docs.z.ai/devpack/tool/others); a coding key on the general base answers
  `429 1113` and vice-versa `400 1211` (`glm.md` §1.1 L26-27 drift note). Choosing the base that matches the key you
  hold is a DEPLOYMENT fact (one base per service, per R1); making the rejection legible is CODE in the GLM provider
  crate, and the reason the two differ is that the status line alone says nothing — `1113` arrives as a
  retryable-looking 429 — while the BODY names the code, which is what a reader must consult to map it.

  CLOSED in a fork: `../glm2api` (a sibling of this repo, not a path inside it) maps GLM's entitlement codes (1113 on the general base, 1211 on the
  coding base) to a legible non-retryable 403/400 that names `provider.base_url` and both product bases, and reads
  the codes when they arrive inside an HTTP 200 — where the pre-gate status read never runs. Deliberately NOT done
  in the template: naming a vendor's numeric codes is provider-crate work (AGENTS §3), and the template has no GLM
  provider to attach them to.
- **G7 — DeepSeek chat + thinking + tools requires `reasoning_content` on prior assistant turns, else 400** (`deepseek.md` §2). Narrowed by the IR reasoning channel: bridges replay client-sent reasoning text, so a client that received thinking through this proxy can replay it through every dialect; none invents a present-but-empty field. What remains is the PRESENT-but-empty case — a tool turn with no thinking text still needs the key on the wire, and writing `reasoning_content: ""` is a DeepSeek-specific request shape, so its home is that provider crate's `to_upstream_body` (§7 item 3), never a bridge, which must not know which vendor answered.
  CLOSED in a fork: `../deepseek2api` injects `reasoning_content: ""` on EVERY assistant turn (absent or
  JSON-null) when the outgoing body declares non-empty `tools`, and forwards any client string byte-for-byte. The
  template keeps its own half — it already replays a present `reasoning_content` verbatim — and the residual here is
  only that the template does not INVENT the field, which is provider work by the same rule.
- **G8 — GLM's Responses gateway wraps errors in HTTP 200** (`{"code":401,"msg":"token expired or incorrect","success":false}`, live probe) → a status-gate is structurally blind to it. Not a template gap: reading that envelope is GLM knowledge, so it lives in the GLM provider crate's buffered path, where the parse already happens. Teaching `gate_response` the shape would put a vendor in a shared crate, which §3 forbids.
  CLOSED in a fork: `../glm2api` detects the 200-wrapped `{code,msg,success:false}` envelope on both the
  buffered and streaming folds, refuses to convert anything carrying `choices` or a success marker (the false-positive
  guard is the test that matters most there), and maps inner codes to their own status instead of relaying a 200.

**Zero-code alternative exists and must not be ignored:** for the *chat* dialect Anthropic is already relay-able through the compat layer (§4 C-column), so the crate is justified by **fidelity** (tools, thinking, prompt caching, `stop_reason` taxonomy, structured output), not by reachability.

### B. Cheap variant: `anthropic-passthrough-relay` (DeepSeek/GLM native `/anthropic`)
For upstreams whose Anthropic surface is a compat shim, the *near-zero-translation* provider is **delivered, not proposed**: it is the fidelity lane (G1) — declare `native_dialects() = [Dialect::Anthropic]` + `relay_raw` and inbound `/v1/messages` folds nothing at all; A4/A5 parses are unnecessary because bytes never touch the IR. Costs that still stand: it can never serve chat- or Responses-dialect clients (those still need the crate's A1–A3 fold), and it relays a knowingly non-faithful Anthropic server (`deepseek.md` §7.8 "we would be relaying a non-faithful Anthropic server") — fidelity to what the vendor actually is, declared rather than hidden.

### C. `*-responses-native` providers (OpenAI / DeepSeek / GLM-coding `/responses`)
No longer blocked: option (i) SHIPPED as the fidelity lane (`native_dialects() = [Dialect::Responses]` + `relay_raw`) and remains the only faithful route — named `response.*` events, reasoning items and chains pass through exactly as the vendor wrote them. Option (ii) — rebuilding a Responses body from IR (`model`, `instructions` from the leading system message, `input` from messages, `max_output_tokens` from `max_tokens`, `reasoning.effort` from `reasoning_effort`) plus a stream parser for named `response.*` events with no `[DONE]` (the compat bridge already emits this grammar: `x2api-dialects/src/responses.rs` header doc) — is for providers that must REWRITE bodies or serve several dialects off one native surface; it no longer loses tool round-trips either, since the IR types them now (G2 CLOSED).

### D. Small core changes worth their cost (each unblocks ≥2 cells)
1. **SHIPPED** — IR reasoning channel (`ChatChunk.reasoning` / `Completion.reasoning`): the compatible `reasoning_content` name is read on both the streamed delta and the buffered message, Anthropic renders and folds `thinking`, Responses renders and folds a `reasoning` item, Gemini deliberately does not (an unsigned `thought` part would be history its own fold rejects) → fixes G-for-thinking on Anthropic + Responses outbound for DeepSeek/GLM/OpenAI(`reasoning_tokens`).
2. **SHIPPED** — `Usage` extension retains cache/reasoning details, with dialect-specific rendering only where the target wire has a field (§1b).
3. **SHIPPED** — `anthropic_kind` → the real vendor table (529/503/402/404/409/413/408/504), with a closed-set test over every status: G4 CLOSED, and a provider crate maps no error kinds.
4. **MOSTLY SHIPPED** — context-aware, admitted model listings: `Provider::models` accepts `CallContext`, and both OpenAI/Gemini listings use the shared gate, admission, and retry path. The reference provider still deliberately keeps its configured credential authoritative. The remaining G5 slice is an Anthropic model-page render/endpoint; Gemini's per-format render already exists.
5. **SHIPPED, but PROVIDER-CRATE work** — vendor-blind in-band 200-error classification now catches OpenAI-shaped `{"error":...}` in transcoded buffered/streamed bodies: trustworthy 4xx-class hints preserve the envelope, while ambiguous/5xx-class bodies become canned permanent 502s. GLM's distinct `{code,msg,success:false}` wrapper still belongs in its provider crate (G8); teaching shared `gate_response` the shape would put a vendor in the shared crate.

## 5. Corrections to the existing four reports (from today's live verification)

1. **`anthropic.md` (a)§7 L178 is superseded in part.** "Zero-code relay? No. `service` cannot reach Anthropic with base_url/key config: wrong path, wrong body keys, strict unknown-field rejection, … non-OpenAI SSE grammar" is true for the **native Messages** endpoint but false for the documented **OpenAI SDK compatibility layer** at `https://api.anthropic.com/v1/chat/completions` (live route: `405 allow: POST` on GET, OpenAI-shaped `401` on POST; official page https://docs.claude.com/en/api/openai-sdk). Correct the verdict to: *chat dialect = NATIVE-compat (relay-able, fidelity-limited); Messages dialect = PROVIDER-CRATE*.
2. **`anthropic.md` (a)§7.6 overstates the error gap.** `openai_error_object` (`crates/x2api-kit/src/errors.rs::openai_error_object`) *does* recognise Anthropic's `error.message`, so messages are relayed verbatim; what the renderer drops is the outer `{"type":"error"}` wrapper and `request_id` (`crates/x2api-server/src/errors.rs::render_anthropic`). `error.type` is no longer on that list — it derives from the vendor's own status table (G4 CLOSED).
3. **`deepseek.md` §7.1 is already satisfied by the IR parser.** `ChatChunk::from_wire` reads `usage` off the frame (not off `choices`), iterates choices, and tolerates a missing `delta` (`crates/x2api-kit/src/types.rs::ChatChunk::from_wire`) — the "never `choices[0]`-index without a guard" hazard cannot occur in the relay path.
4. **`glm.md` §1.1 Responses row confirmed and narrowed**: `https://api.z.ai/api/v1` is a **Coding-Plan** base (official table, docs.z.ai/devpack/tool/others), and the general API documents no Responses endpoint at all (docs.z.ai/llms.txt index) — GLM Responses is therefore entitlement-gated, not general-API.
5. **Probe-methodology caveat**: DeepSeek answers a *bad bearer* with the same JSON 401 for a bogus path (`/v1/jibberish-xyz`, live probe) as for real routes, so 401s there prove auth-ordering, not route existence; Anthropic and GLM do distinguish (404-vs-401 and `code:500 "404 NOT_FOUND"`-vs-`401` respectively), which is what the matrix cells lean on.
