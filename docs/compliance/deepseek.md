# DeepSeek — chat-endpoint compliance vs x2api provider seam

Investigated 2026-09-06 against `api-docs.deepseek.com` (EN + zh-cn, live fetch), the live edge at `api.deepseek.com` (unauthenticated/bad-key probes), plus production-gateway corroboration from local `~/workspace/projects/axonhub` and local `~/.omp/agent/models.yml`. Docs pages are generated from an OpenAPI spec ("Version: 1.0.0", security scheme `http/bearer`) rendered by redoc.

**Verdict: `relay-zero-code`.** DeepSeek's Chat Completions endpoint is a true OpenAI-dialect endpoint (same body, same `chat.completion` / `chat.completion.chunk` envelopes, same `data:`-only SSE with `data: [DONE]`, same `Authorization: Bearer` single-static-key auth, OpenAI-shaped 4xx error envelope). The reference the reference `service` provider provider covers it with `base_url` + key config only — including client-key passthrough via `CallContext::client_authorization`. Three real divergences (below) do **not** require a provider crate as long as `raw` passthrough is used for OpenAI-dialect clients; they only require a crate if you want (a) reasoning → Anthropic `thinking` mapping, (b) param downgrades for strict clients, or (c) native-Anthropic passthrough.

## 2. Request conformance

A plain OpenAI body relays unchanged. Documented parameter set for `chat/completions`: `model` (enum: `deepseek-v4-flash`, `deepseek-v4-pro`, `deepseek-v4-flash-vision-exp`), `messages`, `thinking{type:enabled|disabled}` (default **enabled**), `reasoning_effort` (`low|high|max`; `medium`/`xhigh` **mapped to `high`**), `max_tokens` (**kept name — no `max_completion_tokens` documented**), `response_format` (`text|json_object` only — no `json_schema`), `stop` (string or ≤16), `stream`, `stream_options.include_usage`, `temperature` (≤2, default 1), `top_p` (≤1, default 1), `tools` (function only, ≤128, `strict` = beta), `tool_choice` (`none|auto|required`|named function), `logprobs`, `top_logprobs` (≤20), `user_id` (regex `[a-zA-Z0-9\-_]+`, ≤512).

- **Renamed/dropped:** `frequency_penalty` and `presence_penalty` are marked `deprecated` in the spec — "This parameter is no longer supported. It will not take effect if you pass it to the API" (accepted, ignored). In thinking mode `temperature`, `top_p`, `presence_penalty`, `frequency_penalty` are all documented as no-ops **without error**: "for compatibility with existing software, setting these parameters will not trigger an error but will also have no effect" (guides/thinking_mode).
- **Non-OpenAI extras (forward these verbatim, they are top-level body fields, which is why the OpenAI SDK needs `extra_body`):** `thinking`, `user_id` (OpenAI's `user` is not documented for chat; it *is* the Responses-API name for the same feature). DeepSeek's `max_tokens` stays `max_tokens`.
- **Undocumented OpenAI fields** (`n`, `seed`, `logit_bias`, `best_of`, `max_completion_tokens`, `store`, `metadata`, `modalities`/`audio`, `prediction`, `web_search_options`, `service_tier`, `reasoning`): absent from the spec. **UNVERIFIED** whether ignored or 400/422 — no API key available to probe, and no official statement for the chat endpoint. The closest official evidence is the sibling Responses endpoint: "Unsupported parameters are **silently ignored** and do not cause errors, so existing Responses API clients can connect without modification" (guides/responses_api). Treat passthrough as the default and let the vendor's 400 message tell you otherwise; add a strip-list only if field testing shows rejections.
- **Tool-history requirement (the one real request-side landmine):** in thinking mode with `tools` present, prior assistant turns **must** carry `reasoning_content`, else "the API will return a 400 error" (guides/thinking_mode). Without `tools`, `reasoning_content"is ignored". axonhub encodes this exact workaround: when thinking is on, "`dsReq.Messages[i].ReasoningContent = lo.ToPtr("")`" for every assistant message lacking it. A raw-passthrough relay is fine (client sends what it got); the *Anthropic→OpenAI* direction of our bridge must re-inject `reasoning_content: ""` (or real thinking text) on assistant turns.
- Vision: `content` parts `image_url{url,detail}` and a `file` block (`file_id`/`file_data`) work; images only in `user` messages (400 otherwise); body cap 48 MiB (guides/vision).

## 3. Buffered response conformance

Schema (api/create-chat-completion/"Responses"): `id` (required), `choices[]` (required) with `index`, `message{role:"assistant", content (nullable, required), reasoning_content (nullable), tool_calls[], name?}`, `logprobs` (nullable, required), `finish_reason` **required** with enum `stop|length|content_filter|tool_calls|insufficient_system_resource`; plus `created`, `model`, `system_fingerprint` (required), `object: "chat.completion"`.

- `usage` is **not marked required** in the spec but is present in practice (axonhub buffered/stream fixtures always carry it): `prompt_tokens`, `completion_tokens`, `total_tokens`, **`prompt_cache_hit_tokens`, `prompt_cache_miss_tokens`** (`prompt_tokens` = hit + miss), and `completion_tokens_details.reasoning_tokens`. Our IR `Usage{prompt_tokens, completion_tokens}` keeps the two numbers it models; the cache/reasoning detail is preserved only in `raw` — which is exactly right for OpenAI clients and means Anthropic-dialect clients lose cache accounting (Anthropic's `cache_read_input_tokens` has no feed).
- No `service_tier`, no `choices[].message.refusal`, no `system_fingerprint: null` guarantee. `id` is not guaranteed to be `chatcmpl-…`-prefixed (fixtures show bare 32-hex ids such as `"id":"a032c5d3-f5c9-43df-84f7-5a8ea4944852"`), so never parse the id prefix.

## 4. Streaming conformance

| Aspect | DeepSeek |
|---|---|
| Content type | SSE, "partial message deltas will be sent… as data-only server-sent events (SSE)" — spec wording; no `event:` lines for chat completions |
| Frame grammar | `data: {chat.completion.chunk}` per chunk |
| Terminal sentinel | **`data: [DONE]`** (documented: "消息流以 `data: [DONE]` 结尾" / "with the stream terminated by a `data: [DONE]` message") |
| Chunk fields | `id`, `object:"chat.completion.chunk"`, `created`, `model`, `system_fingerprint`, `choices[].delta{role?, content?, reasoning_content?, tool_calls[]?}`, `choices[].finish_reason`, `logprobs` |
| `reasoning_content` | sits **beside `content` inside the same `delta` object** — official sample: `if chunk.choices[0].delta.reasoning_content: reasoning_content += … else: content += chunk.choices[0].delta.content`. Buffered: sibling field on `message`. Raw passthrough preserves it; the IR `text` field does not |
| Usage chunk | `stream_options.include_usage` **is supported**, with an OpenAI-breaking nuance: "If set to `true`, all chunks in the stream will include a `usage` field, whose value is `null` on every chunk except the last one… Either way, the last chunk before the `data: [DONE]` message carries the token usage statistics… **Note that no separate usage-only chunk is emitted: the statistics ride on the last content chunk, whose `choices` array always contains exactly one element that carries no new content and a non-null `finish_reason`.**" Even with the flag omitted/false, the last chunk still carries usage |
| Keepalive | "Streaming requests: Continuously return SSE keep-alive comments (`: keep-alive`)"; **non-streaming requests return leading empty lines** while queued (guides: rate_limit § Request Keep-Alive) |
| Mid-stream errors | No documented in-stream error frame. **UNVERIFIED** whether DeepSeek ever writes a JSON error frame mid-stream; in-band failure surfaces as `finish_reason: "insufficient_system_resource"` and/or an abrupt close. Pre-stream failures (400/401/402/429/500/503) arrive as normal HTTP status + JSON body, so `stream()`'s status-gate-before-handoff contract holds cleanly |
| Hard cap | "If the request has not started inference after 10 minutes, the server will close the connection" — this bounds inference *start*, not stream length, so a `stream_deadline_secs` duration ceiling never races it: the upstream closes first where it applies, and the relay reports a truncation frame, never a fake-complete answer |

Relay implications (the important part): do **not** detect the usage chunk by `choices.is_empty()`, and do not index `choices[0].delta` unguarded — the terminating chunk's single choice may have `delta` absent entirely (axonhub fixture last line: `{"choices":[{"index":0,"finish_reason":"tool_calls"}], … ,"usage":{…}}`). Handle both shapes (OpenAI-style empty-`choices` usage chunk and DeepSeek's carried-on-last-choice), since a stale copy of DeepSeek's own docs described the OpenAI behaviour (`include_usage`: "an additional chunk will be streamed before the `data: [DONE]`… `choices` field will always be an empty array") and other OpenAI-compatible upstreams behind the same relay do exactly that. Keep-alive comments are harmless to a frame-splitting SSE parser but the leading blank lines on **buffered** responses mean the JSON body must be parsed after whitespace trimming (fine for `serde_json`, fatal for a `bytes→Value` path that assumes offset 0).

## 5. Errors

- Documented statuses (quick_start/error_codes): **400** Invalid Format, **401** Authentication Fails, **402** Insufficient Balance, **422** Invalid Parameters, **429** Rate Limit Reached, **500**, **503**. zh-cn adds 429 cause "请求速率（TPM 或 RPM）达到上限" while the EN page says "sending requests too quickly" and the rate-limit page describes **concurrency** limits (500 v4-pro / 2500 v4-flash / 2500 vision-exp, account-level, "regardless of which API Key"). The WorkBuddy troubleshooting table also maps unknown model to "`Model Not Found` or `404`" — 404 is not in the error-code table.
- Body shape: OpenAI envelope, verified live: `HTTP/2 401` + `content-type: application/json` + `{"error":{"message":"Authentication Fails, Your api key: ****beef is invalid","type":"authentication_error","param":null,"code":"invalid_request_error"}}` (bad bearer). Community sample of a 400: `{"error":{"message":"This response_format type is unavailable now","type":"invalid_request_error","param":null,"code":"invalid_request_error"}}`. Note `code` is a generic `invalid_request_error`, **not** OpenAI's granular `invalid_api_key`/`unsupported_parameter` — so 4xx classification must key off `status`, not `code`. Template rule satisfied: these already are `{"error":{"message":…}}` → pass through verbatim.
- **Plain-text error path (verified):** request with **no** `Authorization` header returns `401` with a *31-byte non-JSON* body `Authentication Fails (governor)` and **no `content-type` header at all** (edge/CloudFront layer, ahead of routing — identical for bogus paths). `gate_response` must not assume JSON on 401/429.
- **Content-type lie:** for some 400s the API returns valid JSON error bodies with `Content-Type: application/octet-stream` (deepseek-ai/DeepSeek-V3#1454, opened 2026-06-24, closed as stale 2026-08-25, unfixed). Parse by body, not header.
- `Retry-After`: **UNVERIFIED / not documented anywhere** on DeepSeek's side; no rate-limit headers (`x-ratelimit-*`) observed in probes, and the docs never mention them. Our `ProviderError.retry_after` will essentially always be `None` for DeepSeek → the template's exponential backoff must be the mechanism; treat 429 as concurrency-driven (retryable) rather than quota-window driven.
- Vendor correlation header present: `x-ds-trace-id` (seen on every probe response) — worth forwarding into `request_id` correlation logging.

## 6. Models endpoint

`GET https://api.deepseek.com/models` (and `/v1/models`; both auth-gated — probed 401 unauthenticated). Shape: `{"object":"list","data":[{"id":string,"object":"model","owned_by":string}]}`; the spec's Model object has **only** those three fields — no `created`, no `state`/`capabilities` (api/list-models). `owned_by` value not shown in docs (**UNVERIFIED**; commonly `deepseek`). Today's enumerable ids are the three `deepseek-v4-*` names. Provider `models()` can be a straight passthrough once the key is configured; a DeepSeek API key is required, so `client_authorization` passthrough works here too.

## 7. Provider-adapter diff list (what `crates/service/src/provider.rs` would have to do)

**Config-only path (recommended):** point the reference `service` provider (`crates/service`) at `https://api.deepseek.com/v1`, bearer key from config or `ctx.client_authorization()` (passthrough is viable: static per-account keys, no token minting, no OAuth, no extra headers), `POST /chat/completions`, gate by status, split on `\n\n`, accept `data:`-only frames, terminate on `data: [DONE]`, set `raw` to each verbatim chunk. OpenAI-dialect clients lose nothing — `thinking`, `reasoning_effort`, `user_id`, `reasoning_content` (buffered and streamed), logprobs, and `prompt_cache_*` all ride through `extra`/`raw`.

Concrete deltas, in priority order:

1. **Usage-chunk detection** — accept usage on a chunk whose `choices[0]` has no `delta` and non-null `finish_reason` (DeepSeek) *and* on `choices: []` (OpenAI); never `choices[0]`-index without a guard. (Docs §stream_options; axonhub fixtures.)
2. **`reasoning_content` is IR-invisible.** `ChatChunk.text`/`Completion.text` are the answer text only; feeding them to the Anthropic bridge emits zero thinking blocks. If faithful Anthropic `thinking` output is wanted, a small provider crate (or an IR extension) must lift `delta.reasoning_content` / `message.reasoning_content` — DeepSeek is the archetypal case where "raw carries it" is true only for OpenAI-dialect clients.
3. **Anthropic→DeepSeek request side:** inject `reasoning_content: ""` on assistant turns when thinking+tools (else 400); emit `thinking:{type}` + `reasoning_effort` from Anthropic `thinking`/`output_config.effort`; never send `reasoning_effort:"none"` (axonhub clears it — chat dialect accepts only `low|high|max` plus compat `medium|xhigh`); `max_tokens` is the correct name (no rename needed); map Anthropic `stop_sequences`→`stop`; `metadata.user_id`→top-level `user_id`.
4. **Param downgrades for strict clients:** `response_format.type: "json_schema"` → `json_object`, drop `json_schema` (chat dialect has no structured-output schema; only the Responses dialect does) — axonhub does exactly this. Community-observed rejection of unavailable `response_format` types (`"This response_format type is unavailable now"`).
5. **finish_reason mapping:** `insufficient_system_resource` is vendor-only → Anthropic `stop_reason` must fall back to `end_turn` (and it should be treated as a retryable upstream failure, since it means "interrupted due to insufficient resource of the inference system"); `content_filter` → `refusal`; `tool_calls` → `tool_use`.
6. **Keep-alive/queue noise:** tolerate `: keep-alive` comment frames mid-stream and leading blank lines in buffered bodies; cap stream lifetime under the 10-minute pre-inference close.
7. **Error hardening:** non-JSON 401 (`Authentication Fails (governor)`), `application/octet-stream` on some 400s, no `Retry-After`, `code` never granular.
8. **Optional native-Anthropic route:** DeepSeek already serves `POST /anthropic/v1/messages` (`x-api-key` supported, `anthropic-version` ignored, unsupported model names silently mapped to `deepseek-v4-flash`, Claude model names mapped opus→v4-pro / haiku|sonnet→v4-flash). A DeepSeek-Anthropic passthrough provider is *also* zero-translation — but note the ignore-heavy compatibility table means we would be relaying a non-faithful Anthropic server, and it cannot supply `raw` OpenAI envelopes.

**Non-chat surfaces** to leave out of v1: `/beta/completions` (FIM, `text_completion` object, `suffix`, ≤4K), `tools[].strict` (needs `/beta`), Files API, `GET /user/balance`, and `POST /responses` (event-SSE, **no `[DONE]`**, terminates on `response.completed|incomplete|failed`; `stream_options` unsupported there).

## 8. Anthropic-dialect obligations (this service is not Anthropic; answered as bridge contract)

Not applicable as an *upstream* requirement — DeepSeek's seam is OpenAI-shaped. What our `/v1/messages` server must satisfy to be a faithful Anthropic face over a DeepSeek-backed provider:

- **Required fields:** `max_tokens` (Anthropic-required; DeepSeek chat treats it as nullable with a model default — validate inbound and pass through), `messages`; `system` accepted as top-level string *and* as `system` role messages (our IR normalizes to a leading system message — DeepSeek's spec lists a `system` message variant, so this round-trips).
- **Auth/version headers:** accept both `x-api-key` and `Authorization: Bearer` inbound (Claude Code uses bearer against `ANTHROPIC_BASE_URL`); accept-and-ignore `anthropic-version` rather than hard-rejecting (DeepSeek itself ignores it); reject/ignore `anthropic-beta` unless we implement files.
- **stop_reason mapping:** `stop`→`end_turn`, `length`→`max_tokens`, `tool_calls`→`tool_use`, `content_filter`→`refusal`, `insufficient_system_resource`→`refusal` or error frame.
- **Content blocks:** must emit `content_block_start/index` per block; reasoning text (from `delta.reasoning_content`) becomes a `thinking` block *before* the `text` block, with `signature` absent — and since DeepSeek gives no signature, either omit `thinking` (safest) or accept a non-faithful unsigned block; `tool_calls` deltas become `input_json_delta`.
- **SSE payloads:** `message_start`(usage: `input_tokens`; `completion_tokens` in `message_delta`), `content_block_start`, `content_block_delta(text_delta|thinking_delta|input_json_delta)`, `content_block_stop`, `message_delta(stop_reason, usage)`, `message_stop`; `event:` lines mandatory (DeepSeek's chat SSE has none — the relay encoder already synthesizes them from IR, and the missing per-chunk usage signal must come from delta #1 in the chain, item 7.1). Cache-read reporting can only come from `raw` (`prompt_cache_hit_tokens`).
- **Errors:** render Anthropic `{"type":"error","error":{"type":…,"message":…}}` from the same `ProviderError` fields, including the non-JSON 401 case (message = the raw text).

## UNVERIFIED (no key, no doc)

Unknown/undocumented OpenAI field handling on chat (`n`, `seed`, `best_of`, `logit_bias`, `max_completion_tokens`, `store`, `user`) · `Retry-After`/rate-limit headers on 429 · mid-stream error frame existence · real `/v1/models` payload contents and `owned_by` value · `max_tokens` default value (docs defer to the pricing page, which lists only "MAX OUTPUT MAXIMUM: 384K") · which exact `tool_choice` × thinking combinations 400 (local `models.yml` carries `supportsToolChoice: false` + `disableReasoningOnToolChoice: true` for both v4 models, and a community repro of `tool_choice:"required"` + `logprobs` + thinking got a 400 — corroborating, not proof) · whether `reasoning_content` and `content` can share one delta (vllm-project/vllm#43933 argues parsers must assume they can; DeepSeek's own sample uses `if/else`, implying they do not).
