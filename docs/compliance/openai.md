# OpenAI Chat Completions — chat-endpoint compliance report (reference dialect)

**Investigated:** official docs at `developers.openai.com` (fetched 2026-09-06; the docs hub moved there from `platform.openai.com/docs` — pages available as `.md`), `platform.openai.com/docs/api-reference/chat`, official SDK source `openai-python` v3.8.0 @ commit `be92815` (2026-09-05) and `openai-node` @ 2026-09-06 HEAD, plus corroborating observed-behavior reports on community.openai.com. All claims cited; `UNVERIFIED` where not confirmable from source/docs.

**TL;DR verdict:** OpenAI is the reference dialect — a base_url+key `service` provider is compliant with **zero provider code**. The compliance risks are not in the envelope (byte-verbatim OpenAI) but in (a) model-lineup churn (GPT-6 Astra has no Chat-Completions function calling; reasoning models 400 on stale fields), (b) strict unknown-argument rejection that makes *outbound* field-stuffing dangerous, and (c) the template's deliberate Retry-After non-copy, which against OpenAI you *want* to opt into.

---

## 1. Endpoint + auth

| Item | Value | Source |
|---|---|---|
| Chat create | `POST https://api.openai.com/v1/chat/completions` | API reference / all SDK examples |
| Models | `GET https://api.openai.com/v1/models` | https://developers.openai.com/api/reference/resources/models/methods/list |
| Auth | `Authorization: Bearer <api-key>` only. No `x-api-key`, no version header | official curl in every doc example |
| Optional routing headers | `OpenAI-Organization: <org_id>`, `OpenAI-Project: <proj_id>` — sent only when configured | SDK `src/openai/_client.py:641-642` (verbatim: `"OpenAI-Organization": self.organization ... Omit(), "OpenAI-Project": self.project ... Omit()`) |

Client-key passthrough via `CallContext::client_authorization` is **fully viable**: an OpenAI API key is a static bearer secret; no OAuth/token management. Optional: honor inbound `OpenAI-Organization`/`OpenAI-Project` by forwarding them (SDK shows they are plain header echoes).

**Base URL drift (current, 2026).** Besides global `api.openai.com/v1`, OpenAI now operates regional **data-residency prefixes** `<region>.api.openai.com` — `us`, `eu`, `au`, `ca`, `jp`, `in`, `sg`, `kr`, `gb`, `ae` — usable per-request with a Global-project key ("As an alternative to creating a region-specific project, you can select regional processing for an individual request by using the prefixed domain", verbatim). Regional *processing* for `/v1/chat/completions` exists only in US, EU, UAE; EU/AE require MAM/ZDR approval; non-US regions **reject `store=true`** ("Cannot set store=true in non-US regions"); regional endpoints carry a documented **10 % uplift for models released on/after 2026-03-05**. Source: https://developers.openai.com/api/docs/guides/your-data (Data residency section). Legacy: the 2022 `/v1/engines` endpoint is gone; there is no `/v2/v3/v4` path — `/v1` has been stable. Note the docs *hub* moved (platform.openai.com → developers.openai.com), the API itself did not.

## 2. Request conformance (plain OpenAI JSON body)

A plain `chat.completions` body works unchanged — **but only for fields OpenAI still knows, with values the target model still tolerates**. OpenAI's request surface (complete inventory, `openai-python/src/openai/types/chat/completion_create_params.py` @ 3.8.0): `messages`*, `model`*, `audio`, `frequency_penalty`, `function_call`(dep), `functions`(dep), `logit_bias`, `logprobs`, `max_completion_tokens`, `max_tokens`(dep), `metadata`, `modalities`, `moderation`, `n`, `parallel_tool_calls`, `prediction`, `presence_penalty`, `prompt_cache_key`, `prompt_cache_options`, `prompt_cache_retention`(dep), `reasoning_effort`, `response_format`, `safety_identifier`, `seed`, `service_tier`, `stop`, `store`, `stream`, `stream_options`, `temperature`, `tool_choice`, `tools`, `top_logprobs`, `top_p`, `user`(dep), `verbosity`, `web_search_options`.

- **max_tokens vs max_completion_tokens.** SDK verbatim on `max_tokens`: *"This value is now deprecated in favor of `max_completion_tokens`, and is not compatible with o-series models."* `max_completion_tokens` is accepted by **all** models ("works on all models but max_tokens doesn't work on the new models" — corroborated at help.openai.com article 5072518: "For reasoning models like o3 and o4-mini, use max_completion_tokens … For earlier/non-reasoning models, max_tokens still works"). **As of 2026 `max_tokens` is still accepted** (not removed) on classic models — UNVERIFIED whether a removal date is announced; it remains in the 3.8.0 spec.
- **`stream_options`** `{include_usage, include_obfuscation}` — accepted, only with `stream: true` (SDK docstring: "Only set this when you set `stream: true`").
- **`response_format`** — accepted, incl. `{"type":"json_schema",...}` Structured Outputs (SDK docstring verbatim).
- **`tools`/`tool_choice`** — accepted; `functions`/`function_call` deprecated but still in spec. **Big 2026 caveat:** official reasoning guide states verbatim *"Chat Completions does not support function calling with GPT-6 Astra"* — a tool-laden body relays fine only to non-Astra models. (https://developers.openai.com/api/docs/guides/reasoning)
- **Model-gated values that 400** despite being valid field names: `reasoning_effort` values are model-dependent (`none|minimal|low|medium|high|xhigh|max` in spec; "Not all reasoning models support every value" SDK verbatim; gpt-6-astra rejects `none` with HTTP 400 per reasoning guide). `temperature`/`top_p` are default-only on o-series/GPT-5-family: observed 400 verbatim *"Unsupported value: 'temperature' does not support 0.2 with this model. Only the default (1) value is supported."* type `invalid_request_error`, code `unsupported_value` (community.openai.com/t/gpt-5-models-temperature/1337957; official migration guidance per community.openai.com/t/1369113: on GPT-5.x `temperature`/`top_p`/`logprobs` supported **only** with `reasoning_effort: none`). Same for `reasoning_effort` sent to non-reasoning models ("Invalid 'reasoning_effort' for non-reasoning model", community.openai.com/t/1341785).
- **Unknown arguments are rejected, not ignored:** OpenAI answers `400 {"error":{"message":"Unrecognized request argument supplied: <field>","type":"invalid_request_error","param":null,"code":null}}` (observed verbatim for `enable_thinking`, `streaming`, `text` at community.openai.com/t/1265200, /t/564298, /t/1152080). This is why a *stateful* relay that accumulates per-vendor extras must scrub them before pointing at OpenAI.
- **`store`** accepted (distillation/evals retention); forced `false` under ZDR orgs; **400-class blocked** (`cannot set store=true`) on non-US regional endpoints. `user` is officially migrating: SDK verbatim *"This field is being replaced by `safety_identifier` and `prompt_cache_key`."*
- **IR fit:** `ChatRequest.extra` merged back via `to_value()` means the relay body is exactly what an OpenAI client sent — no transform needed for OpenAI itself.

## 3. Buffered response conformance

Full `chat.completion` object, no-optional-stripping risk for the IR: `id`, `object: "chat.completion"`, `created` (unix secs), `model`, `choices[].{index, message{role, content|null, refusal, tool_calls, annotations, audio}, finish_reason, logprobs}`, `usage`, plus `service_tier`, `system_fingerprint`, `metadata`, and — new in 2026 — `moderation` (input/output moderation results when the `moderation` request policy is set). `finish_reason` enum verbatim: *"`stop` … `length` … `content_filter` if content was omitted due to a flag from our content filters, `tool_calls` if the model called a tool, or `function_call` (deprecated)"*. (API reference chat object, extracted 2026-09-06.)

- **usage is unconditional in buffered mode** — no `stream_options` opt-in. Field names `prompt_tokens` / `completion_tokens` / `total_tokens` match the IR `Usage` exactly; `completion_tokens_details.reasoning_tokens` and `prompt_tokens_details.cached_tokens` are extras the IR legitimately drops (reasoning tokens ARE billed inside `completion_tokens`).
- `message.content` is `null` on tool-call-only turns — the IR's `text` becomes "" but `raw` preserves everything; Anthropic bridge must treat null-content as empty text. [confirmed by SDK types: `content: Optional[str]`]

## 4. Streaming conformance

- **Content-Type:** `text/event-stream` (template `is_sse()` `starts_with("text/event-stream")` matches).
- **Frame grammar:** `data: <json>\n\n` records, **no** `event:` lines for chat completions, terminal sentinel verbatim **`data: [DONE]`**. Official (API reference, `stream_options.include_usage`): *"If set, an additional chunk will be streamed before the `data: [DONE]` message. The `usage` field on this chunk shows the token usage statistics for the entire request, and the `choices` field will always be an empty array. All other chunks will also include a `usage` field, but with a null value."* With `include_usage:false`/absent there is **no usage chunk at all**; `ChatChunk.usage` stays `None` and the Anthropic bridge's final `usage` degrades — document that relay clients must send `stream_options` if they want token counts. NOTE also verbatim: *"If the stream is interrupted or cancelled, you may not receive the final usage chunk."*
- **Chunk object:** `chat.completion.chunk` with fields `id`, `choices[] (delta…)`, `created`, `model`, `object`, and optional `moderation`, `obfuscation`, `service_tier`, `system_fingerprint`, `usage`. Two relay hazards:
  1. **`obfuscation`** — SDK/API-reference verbatim: random-padding string "included by default and omitted when `stream_options.include_obfuscation` is `false`". It rides through in `raw` (harmless to OpenAI-dialect clients, noise to Anthropic bridge). A relay pointing at OpenAI should NOT force it off unless bandwidth matters; a relay pointing at *other* vendors must not send `include_obfuscation` (unknown-arg risk).
  2. **usage-null chunks**: every chunk carries `"usage": null` under include_usage — must deserialize into `Option<Usage>` (serde `null` → None; fine in Rust, breaks naive `.unwrap()` JSON handling).
- **Keepalives:** OpenAI does not document comment keepalives for chat-completions streams — **UNVERIFIED** whether the backend ever emits `:` lines; the official decoder skips them (SDK `SSEDecoder.decode` verbatim: `if line.startswith(":"): return None`), as does the template `SseDecoder`. Treat comment frames as legal-but-unexpected.
- **Mid-stream errors:** for chat completions, error-after-start behavior is **not documented** (UNVERIFIED wire shape). The official SDK defensively treats a *data* payload containing an `error` object, or a named `event: error` frame, as a terminal APIError (`_streaming.py` verbatim: `if is_mapping(data) and data.get("error"): … raise APIError(...)`). A relay should map any in-stream `error` key to a terminal `ProviderError` — which the template's guarded stream already does (truncation chunk, `[DONE]` withheld). Also: normal end-of-stream is `[DONE]`; a bare EOF without it is possible on interruption ("may not receive the final usage chunk").

## 5. Errors

- **Envelope:** `{"error": {"message", "type", "param", "code"}}` — exactly the template's `openai_error_object` pass-through shape, so vendor bodies land verbatim. 401/400/403 bodies observed as `{"error":{"message":"...","type":"invalid_request_error","param":"temperature","code":"unsupported_value"}}`.
- **Statuses/codes** (official https://developers.openai.com/api/docs/guides/error-codes, fetched 2026-09-06): 400 `invalid_request_error` (incl. invalid `service_tier`, unrecognized argument); 401 auth ("Incorrect API key provided", "IP not authorized"); 403 region unsupported; **429 family**: plain rate limit (type `rate_limit_exceeded`), **`slow_down`** (type `rate_limit_error`, code `slow_down` — ramp-rate limiting, new 2026), `credit_balance_exhausted`, `organization_spend_limit_exceeded`, `project_spend_limit_exceeded`, `organization_usage_limit_exceeded` (billing ones have type `insufficient_quota` — "The broader `error.type` can still be `insufficient_quota`", verbatim); **503** (new): *"Type: `service_unavailable_error`, Code: `server_is_overloaded` — The requested model is temporarily overloaded"*; 500.
- **Retry-After:** official (rate-limits guide, verbatim): "`Retry-After` … The minimum number of seconds to wait before retrying a temporary rate-limit error, **when present**" on **429 and 503** only; may be absent (fall back to exponential backoff + jitter). Related headers on responses: `x-ratelimit-{limit,remaining,reset}-{requests,tokens,project-tokens}`. In practice OpenAI also emits **`retry-after-ms`** (nonstandard; the official SDKs parse it *first*: `_base_client.py` verbatim `for header, divisor in (("retry-after-ms", 1000), ("retry-after", 1))`, then fall back to parsing `Retry-After` as **HTTP-date** via `email.utils.parsedate_tz` — so a relay parser must accept int seconds, nonstandard float seconds, and IMF-fixdate). SDK retry policy for reference: default 2 retries; honor server delays **up to 120 s** (`MAX_RETRY_AFTER_DELAY = 2*60`; delays above it suppress retry: "Honor server-directed delays up to two minutes"), backoff `0.5*2^n` capped 8 s ±25 % jitter; honors nonstandard **`x-should-retry: true|false`** ("Note: this is not a standard header"); retries 408/409/429/≥500.
- **Template interaction:** `gate_response` deliberately does NOT copy upstream `Retry-After` ("the free-tier folklore … is that vendors advertise hours"). OpenAI's advertised values are seconds-scale and the docs instruct honoring them — so the OpenAI provider *should* parse `retry-after-ms`/`retry-after` (both forms) and `with_retry_after(cap at ~120s)`, and the retry loop should treat **503/429 identically** as retryable. This is polish, not a compliance failure: without it the relay still returns correct status + envelope to its clients.

## 6. Models endpoint

`GET /v1/models`, `Authorization: Bearer` required (401 otherwise; every official example passes the key). Shape (API reference verbatim, note the **new** field): `{"object":"list","data":[{"id":"model-id-0","object":"model","created":1686935002,"owned_by":"organization-owner","shutdown_date":null}, …]}` — `shutdown_date` is *"The date when the model will shut down, or null if not announced"* (`optional string or null`), a 2026 addition tracking the aggressive deprecation calendar. A verbatim-passthrough relay carries it in `Value`; a *typed*-relay to other vendors must treat it optional. Model-name churn is the real signal here: the current lineup (batch/data-residency tables) is `gpt-6-astra`, `gpt-5.6-sol|terra|luna`, `gpt-5.5-2026-04-23`, `gpt-5.4*`, `gpt-5.2/5.1/5*`, `gpt-4.1*`, `o3/o4-mini/o1`, `gpt-4o*`, with dated snapshots + alias twins; gpt-4o family and gpt-4/3.5 snapshots **shut down 2026-10-23**, older GPT-5/o3 snapshots **2026-12-11** (https://developers.openai.com/api/docs/deprecations). Hardcoding any allowlist in relay configs goes stale in months — always pass `/v1/models` through.

## 7. Provider-adapter diff list (OpenAI ↔ our IR)

What the service provider's request/response translation would do, which is exactly what the reference relay already does:

| Direction | Transform | Relay status |
|---|---|---|
| request | `req.to_value()` → POST `{base}/chat/completions`, `Authorization: Bearer <key>` (configured or `ctx.client_authorization()`); `stream` field as-is; optionally inject `stream_options.include_usage` when the inbound client requested it (it arrived in `extra` anyway) | **identity** |
| buffered | gate → parse `chat.completion`; `raw=Some(full JSON)`; `text = choices[0].message.content` (null→""); `finish_reason`, `usage` map 1:1 | identity |
| stream | gate-before-handoff (OpenAI returns 4xx as JSON **before** the first SSE frame) → decode `data:` frames → break on `[DONE]`, else each frame → `ChatChunk{raw, text=delta.content, finish_reason, usage}` | identity |
| errors | `openai_error_object` matches OpenAI natively → verbatim passthrough of 4xx bodies; 5xx canned (incl. 503 `server_is_overloaded` — retryable, see Q5) | identity + optional retry-after parse |
| models | GET `{base}/models` → verbatim `Value` | identity |

Zero-translation gaps: none. Recommended (not required) relay provider options, all config-not-code: (1) parse+capped-forward `Retry-After`/`retry-after-ms`; (2) when the SAME relay instance also fronts other vendors, strip OpenAI-only extras (`stream_options`, `store`, `metadata`, `moderation`, `service_tier`, `prompt_cache_*`, `safety_identifier`, `prediction`, `audio`, `modalities`, `web_search_options`, `verbosity`, `reasoning_effort`, `parallel_tool_calls`, `n>1`, `logit_bias`, `seed`) from that vendor's body — OpenAI-shaped vendors without these fields answer `400 Unrecognized request argument supplied` (proven against OpenAI itself; stricter third parties do the same); (3) never map `max_tokens`→`max_completion_tokens` silently for gpt-5/o-style models, but DO expect naive clients to 400 there and pass the 400 through; (4) for gpt-6-astra, `tools` on chat completions is unsupported — pass the 400 through rather than translating to Responses (that would be a new provider crate, out of scope for a relay).

### Caveats / gotchas (condensed)

1. **`[DONE]` absence on interruption** — final usage chunk and even `[DONE]` can vanish if the stream is cancelled server-side; relay must treat bare EOF as normal-ish termination but honor its own `stream_deadline`/truncation rules. `[DONE]` presence is documented; EOF-without-`[DONE]` is stated only as "you may not receive the final usage chunk".
2. **Obfuscation padding is ON by default** on streams — bandwidth, and non-OpenAI re-emitters (Anthropic bridge ignores it via text mapping; fine).
3. **`"usage": null` on every streamed chunk** under include_usage — deserializers must accept null.
4. **Two different 429 `type` spellings** exist (`rate_limit_exceeded` vs `rate_limit_error`+`slow_down`) — don't type-match; status-match.
5. **503 `server_is_overloaded`** is now a first-class retryable response; retry policies that only treat ≥500-with-no-body or 429-as-retryable miss the documented contract (and the openai-python HEAD commit of 2026-09-05 was precisely "document throttling and model overload responses").
6. **Docs drift velocity is the real cost**: model families, deprecation dates (2026-10-23 / 2026-12-11 shutdowns), regional `store=true` bans, 10 % regional uplift, GPT-6 Astra's chat-completions capability cut (no function calling), and per-model parameter vetoes — none of which change the envelope. A relay is structurally compliant; it just must not hardcode model or field assumptions.
7. **Passthrough auth viability:** static bearer key; `CallContext::client_authorization` works as-is; org/project headers optionally forwarded. No token lifecycle needed.
8. The `metadata`/`moderation` request fields + `shutdown_date` in `/v1/models` + `moderation` in responses are 2026-era additions present in SDK 3.8.0; older "OpenAI-compatible" clones won't have them — another argument for scrubbing OpenAI-only extras when fanning out.

**Verdict: `relay-zero-code`** — the reference `service` provider with `base_url=https://api.openai.com/v1` + key config is a compliant OpenAI provider for complete, stream, and models; the only judgment calls (retry-after forwarding, 503 retryability, extras scrubbing) are behavior *polish* the reference relay can adopt generically, not OpenAI-specific code.
